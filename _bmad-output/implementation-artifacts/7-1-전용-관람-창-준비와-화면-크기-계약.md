# Story 7.1: 촬영 전 전용 관람 창 준비와 화면 크기 계약

Status: done

Correct Course Note: 2026-08-11 승인된 구현 준비성 보정에 따라 기존 Story 7.1을 분할했다. 이 Story는 app-lifetime viewer readiness와 physical display-size contract만 소유한다. Immutable sample publication, opaque double-buffer, actual monitor-present 계측, visible standby/hidden prewarm A/B는 Story 7.2가 소유한다.

## Story

booth customer로서,
촬영 전에 전용 관람 화면이 올바른 모니터와 현재 세션에 준비되어 있길 원한다.
그래서 이후 어떤 이미지 경로를 사용하더라도 신뢰할 수 있는 고객 화면에서 촬영을 시작할 수 있다.

## Scope Boundary

### In Scope

- app-lifetime read-only viewer window
- approved customer monitor targeting
- current-session binding과 readiness handshake
- monitor profile, photo rectangle, DPR, physical display-fit contract
- listener-ready, layout-ready, viewer epoch, snapshot revision
- reload, listener loss, revision-gap reconciliation
- viewer 미준비 또는 stale epoch일 때 capture eligibility 차단
- viewer contract, automated tests, HV-13A hardware evidence

### Explicitly Out of Scope

- request-scoped immutable sample generation
- atomic display-pointer publication
- opaque double-buffer swap
- trusted-input-to-actual-present measurement
- visible standby versus hidden prewarm A/B
- LibRaw embedded JPEG 또는 RAW+JPEG source 선택
- display-fit preset proxy 생성
- resident renderer
- RAW-refined seamless swap
- 100-shot 또는 최종 출시 승인

위 항목은 Story 7.2부터 Story 7.10이 소유하며 Story 7.1의 완료를 위해 끌어오지 않는다.
**이 Story는 관람 창에 사진을 표시하지 않는다.** 사진을 놓을 자리(photo rectangle)와 그 자리에 필요한 픽셀 수를 계약으로 확정할 뿐이다.

## Acceptance Criteria

1. Given 유효한 세션이 승인된 부스 하드웨어에서 시작되었을 때, when capture eligibility를 평가하면, then 전용 read-only viewer가 승인된 고객 모니터에 이미 생성되어 있어야 하고 현재 session binding, monitor profile, photo rectangle, DPR, listener readiness, layout readiness를 보고해야 한다.
2. Given 승인된 1080p, 1440p, 4K display profile 중 하나가 활성화되었을 때, when viewer가 필요한 source dimension을 계산하면, then 실제 photo rectangle과 DPR에서 physical display-fit class를 계산해야 하고 고정 384px thumbnail이나 upscaled review-rail asset을 적합한 source로 취급하면 안 된다.
3. Given viewer reload, listener loss, snapshot revision gap, 또는 viewer epoch 변경이 발생했을 때, when readiness를 복구하면, then monotonic host snapshot에서 최신 session binding과 display profile을 다시 읽어야 하고 stale epoch 상태로 capture-ready를 유지하면 안 된다.
4. Given production viewer surface가 고객에게 표시될 때, when surface를 검사하면, then editing, deletion, preset selection, navigation, diagnostic control이 없어야 하고 readiness failure는 booth control surface의 truthful wait/call guidance로만 전달되어야 한다.
5. Given 구현과 자동 테스트가 완료되었을 때, when Story 7.1 closure를 검토하면, then HV-13A가 pre-capture viewer readiness, approved monitor targeting, current-session binding, physical display-size contract를 `Go`로 기록하기 전까지 `review`에 머물러야 한다.

### HV-13A No-Go 보정 (2026-08-11, run-20260811-135652)

실장비 판정: `No-Go`. 관람 창 재생성이 30초 이상 반환되지 않고 새 창이 흰 화면에서 복구되지 않았다.

- [x] **근본 원인 1 — main thread 교착.** `#[tauri::command]`는 기본이 blocking 실행이라 event loop가 도는 main thread에서 실행된다(`tauri-macros` `ExecutionContext::Blocking` → `body_blocking`). 그 안에서 `WebviewWindowBuilder::build()`를 부르면 event loop가 자기 응답을 기다리는 교착이 된다. 창은 생성되지만 절대 그려지지 않고 호출도 반환되지 않는다. 앱 setup에서는 event loop가 아직 없어 정상 동작했기 때문에 최초 생성만 성공했다.
  - [x] `ensure_viewer_window` command를 `#[tauri::command(async)]`로 바꿔 sync threadpool에서 실행한다.
  - [x] main thread에서 창 생성이 요청되면 background 스레드로 넘기는 가드를 추가한다 (`should_offload_window_creation`).

### 최우선 설계 결정: session binding은 host가 소유해야 한다

현재 `sessionId`는 React `SessionProvider`(`src/session-domain/state/session-provider.tsx`)의 `sessionDraft.sessionId`에만 존재한다. 호스트 명령은 전부 `sessionId`를 인자로 받는 무상태 구조다 (`get_capture_readiness(input.session_id)` → `SessionPaths::new(base_dir, session_id)`).

`viewer-window`는 **별개의 WebView이고 별개의 React root**다. booth window의 React 상태에 접근할 수 없다. 따라서:

- viewer가 "현재 세션"을 알 유일한 방법은 host가 소유한 binding을 읽는 것이다.
- React가 두 창 사이에서 세션을 전달하려 하면 안 된다. `localStorage`, `BroadcastChannel`, URL query로 sessionId를 옮기는 우회는 **금지**한다. host-normalized truth 원칙 위반이며 stale epoch 방어가 불가능해진다.
- T2를 먼저 끝내야 T3~T5가 성립한다.

### 아키텍처 가드레일 (위반 시 리뷰 반려)

- React 컴포넌트에서 `invoke()`를 직접 호출하지 않는다. 모든 host 호출은 `src/viewer-surface/services/viewer-host-adapter.ts`를 거친다.
- Rust command는 `src-tauri/src/commands/`의 얇은 진입점이고, 도메인 로직은 `src-tauri/src/viewer/`에 둔다.
- 계약 정의는 TS/Rust 한 쌍만 존재한다. 세 번째 정의를 만들지 않는다.
- snapshot이 durable recovery 경계다. live event만으로 readiness를 소유하지 않는다. viewer는 마운트/재연결마다 `get_viewer_readiness()`를 한 번 읽고 시작한다.
- `sessionId`, `viewerEpoch`, `revision`, `monitorProfile`은 모든 payload에 명시적으로 싣는다.
- 오래된 revision을 받으면 무시한다. 큰 revision만 적용한다.

### Tauri / WebView2 구현 세부

- Tauri `2.10.3`, `@tauri-apps/api` `^2.10.1`. Tauri v2 API만 사용한다 (v1 문법 금지).
- `app.emit(...)`은 **모든 window에 브로드캐스트**한다. 한 창만 대상으로 하려면 `emit_to("viewer-window", ...)`를 쓴다. 기존 `capture-readiness-update`는 브로드캐스트이므로 viewer도 수신한다는 점을 인지한다.
- capability 파일 없이 만든 window는 IPC 권한이 0이다. T3의 `viewer-window.json`은 선택 사항이 아니다.
- `main.tsx`는 `<StrictMode>`를 쓰므로 dev에서 effect가 2회 실행된다. listener 등록은 idempotent해야 하고, 기존 `session-provider.tsx`의 `isDisposed` + unlisten 패턴을 따른다.
- WebView2는 background/hidden window의 타이머를 throttle한다. viewer가 스스로 "나는 살아 있다"고 주장하는 주기에 의존하지 말고, host가 마지막 report 시각을 host clock으로 평가한다.
- 이미지 bytes를 IPC로 옮기지 않는다 (이번 Story에서는 이미지 자체를 다루지 않지만 계약이 그 방향을 막지 않아야 한다). 기존 `assetProtocol.scope` 정책을 유지한다.
- DPR truth: Rust `Monitor::scale_factor()`와 WebView `window.devicePixelRatio`는 어긋날 수 있다. **required source dimension 계산의 truth는 viewer가 보고한 실제 CSS rect × `window.devicePixelRatio`**이고, monitor profile은 승인 여부 판정용이다.

### Physical display-fit contract (AC 2)

3:2 contain 기준. `requiredSource = ceil(cssRect × DPR)`이며 **upscale은 0이어야 한다**.

| Display profile | 예상 photo rect | 최소 필요 photo pixels | 기본 proxy class |
| --- | --- | ---: | ---: |
| 1920×1080, DPR 1 | 약 1620×1080 CSS | 약 1620×1080 | 1920×1280 |
| 2560×1440, DPR 1.25 | 약 1728×1152 CSS | 약 2160×1440 | 2592×1728 |
| 3840×2160, DPR 2 | 약 1620×1080 CSS | 약 3240×2160 | 3456×2304 |

적합 판정 규칙: `naturalWidth ≥ requiredSourceWidthPx && naturalHeight ≥ requiredSourceHeightPx`. 표의 proxy class는 Story 7.4가 생성할 목표값이고, Story 7.1은 **필요 픽셀 수를 계산해 보고하는 것까지만** 소유한다.

384px thumbnail은 어떤 profile에서도 이 조건을 만족하지 못한다. 테스트로 명시 고정한다.

### UX 가드레일

- viewer는 read-only다. 조작 요소와 진단 요소가 0이어야 한다.

### 명명 규칙 (아키텍처 강제)

- Rust command: `snake_case` (`get_viewer_readiness`)
- TS wrapper: `camelCase` (`getViewerReadiness`)
- event 이름: `dot.case` 네임스페이스가 아키텍처 규칙이지만, **현재 코드베이스는 kebab-case(`capture-readiness-update`)를 쓰고 있다.** 일관성을 위해 기존 kebab-case를 따르고, 이 편차를 story completion note에 기록한다.
- JSON 필드: TS 경계는 `camelCase`, Rust 내부는 `snake_case` + `#[serde(rename_all = "camelCase")]`
- React 컴포넌트/파일: `PascalCase.tsx`. 훅 파일은 현재 코드베이스 관행대로 `use-kebab-case.ts`이고 export는 `useCamelCase`다 (`src/app/providers/use-capability-service.ts` 참조). 아키텍처 문서의 `useSessionState.ts` 예시와 다르지만 **실제 코드 관행을 따른다.**
- 도메인 디렉터리: `kebab-case` (`viewer-surface`)
- 타임스탬프: 경계에서 ISO 8601 / RFC3339, 내부 계측은 `*AtMs` epoch millis (기존 `readyAtMs`, `visibleAtMs` 관행)

### 절대 하지 말 것 (disaster prevention)

1. `tauri.conf.json`의 `app.windows`에 viewer를 추가하지 않는다. 세션과 무관하게 항상 뜨고 monitor targeting을 코드로 제어할 수 없다.
2. `SurfaceAccessGuard`를 `/viewer`에 쓰지 않는다. 실패 시 `/booth`로 이동해 고객 모니터에 조작 화면이 뜬다.
3. viewer readiness를 `<img onLoad>`, file 존재, renderer-ready로 판정하지 않는다. 이번 Story의 readiness는 window/listener/layout/binding 뿐이다.
4. `src-tauri/src/render/mod.rs`의 384px 상수를 바꾸지 않는다. renderer 변경은 Story 7.4 범위다.
5. immutable generation, display pointer, double-buffer, present telemetry를 만들지 않는다. Story 7.2 범위이며 끌어오면 두 Story의 evidence가 오염된다.
6. 자동 테스트 통과만으로 `done` 처리하지 않는다. HV-13A `Go` 없이는 `review` 유지다.
7. viewer가 없을 때 capture를 조용히 허용하지 않는다. AC 1의 핵심은 차단이다.
8. cross-session 자산·상태가 viewer로 새지 않게 한다. NFR-004 위반은 0 tolerance다.

### Previous story intelligence

Story 7.1은 Epic 7의 첫 Story라 직전 번호 Story가 없다. 다만 같은 표시 경로를 다룬 Story 1.9(`review`, hardware `No-Go`)의 학습이 직접 적용된다.

- **in-place overwrite는 승인되지 않는다.** Story 1.9는 하나의 canonical JPEG 경로를 덮어쓰는 구현으로 만들어졌고, 2026-08-11 보정에서 superseded historical evidence로 강등됐다. viewer 계약도 같은 원칙을 따라야 한다 — 상태는 revision으로 전진하고, 과거 값을 덮어쓴 뒤 "최신"이라 주장하지 않는다.
- **자동 테스트 전부 통과 + 실장비 실패**가 실제로 일어났다. Story 1.9는 Rust/TS/.NET 검증을 모두 통과했지만 실장비에서 fast preview가 한 번도 고객 화면에 도달하지 않아 `No-Go`가 됐다. HV-13A 증거 계획을 구현과 동시에 준비한다.
- **delayed/duplicate 이벤트가 최신 슬롯을 오염시킨 회귀**가 code review에서 2건 나왔다 (2026-04-03). viewer도 동일 위험이 있다: 늦게 도착한 이전 epoch의 report가 현재 epoch readiness를 덮으면 안 된다. epoch + revision 이중 방어를 처음부터 넣는다.
- **correlation key를 프론트에서 생성해 끝까지 잇는 방식**이 유효했다 (`requestId`). viewer도 `viewerEpoch`를 host가 발급하고 모든 report에 실어 되돌려받는 구조로 간다.
